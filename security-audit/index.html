How we use Cloudflare's security-audit skill

Cloudflare open-sourced the skill that its internal vulnerability scanner grew out of (MIT licence). This page covers what it does, the order we run it on our projects, how Closefast's first run is set up, and how it keeps running after that.

In one line: install the skill pinned to one commit, run a full audit on Closefast first (live sending, multi-account, wallet), fix every confirmed finding with a regression test, run it again (one run finds about half of what repeated runs find), then move to One-Click Launch and the email engines. After that, a smaller audit runs on the changed code before any deploy that touches login, money, sending or replies.

1. What the skill is

It's a set of instructions for a coding agent (here, me in Claude Code) to split a security audit across many separate agents, so no single context fills up and no agent gets to grade its own work. It runs six phases:

1. MapRecon agents map the architecture, trust boundaries and every input, and write a coverage ledger: each part of the code paired with the attack classes that apply to it.
2. HuntOne isolated hunter per ledger unit tries to break the code. Coverage critics then look for units nobody checked and send hunters to them.
3. DisproveEvery candidate goes to a fresh verifier whose job is to prove it wrong. The agent that found a bug never confirms it.
4. RecordFindings are written to findings.json in a fixed schema with one of three verdicts (confirmed, needs validation, rejected), and two scripts check them mechanically.
5. Re-verifyNew agents check every final claim against the source again.
6. ReportREPORT.md, FINDINGS-DETAIL.md and NEEDS-VALIDATION.md are written from the verified records only.

The rules that keep the findings honest:

  • A finding has to name who the attacker is, which boundary they cross and what they end up with. Missing best practice alone doesn't count.
  • Severity follows demonstrated impact.
  • Anything that depends on settings outside the code (Cloudflare dashboard, provider config) stays "needs validation" with the exact fact that's missing.
  • Runs add up: a second run reads the first one's ledger, re-checks code that changed and hunts what was left uncovered.

I read the whole skill before adopting it: 12 instruction files, 10 attack-class files, the JSON schema and the two validators. The validators only read and write files: no network calls and no processes spawned outside their own tests.

2. What it adds over our 7 Nov security pass

The 7 Nov pass on Closefast was one checklist review. It found 25 issues (1 critical, 5 high, 11 medium, 8 low). 24 are fixed, and one is a tracked baseline that only shrinks.

3. Where we run it, in order

Ordered by what a bug could cost: real people emailed, real money moved, real customer accounts. The cap is the most agent runs a single audit may use. The skill stops and reports instead of going over it.

5. Where the hunters start

The ledger covers everything in scope. These five areas get the first hunting wave, because they're where Closefast touches money, strangers or other accounts:

1. Autopilot repliesA prospect's reply is drafted into an answer and sent without a human. Can text in that reply change what we send, who we send it to, or pull the brief's private notes into the email? (AI and LLM)
2. Text from outsideLinkedIn posts, homepage text and imported CSVs all reach the writer and the support agent. Can any of them act as instructions? (AI and LLM)
3. Account boundariesReplies to the shared inbox are routed between accounts. Can one account read or act on another account's leads, replies, wallet or erased data? (data isolation)
4. Money and spendCredits, the wallet ledger, Dodo webhooks, welcome credits, and the data and Signals caps. Can anyone mint credits, replay a payment, or run up our provider bills? (spend, webhooks)
5. Login and the operator keySessions, Google account linking, password reset, the operator token's reach, and the admin console rendering prospect content. (web auth, client side)

6. Run safety rules

  • Read-only on source. No request to the production app, no reads or writes to the production database, no emails, no deploys while the run is going.
  • Agents get the exported source copy and their own scratch folder. They never see ~/.closefast_cloud_*, ~/.cloudflare_keys or any other key file.
  • Only dummy accounts, dummy keys and local fixtures. No paid API calls (treg, OpenRouter, Instantly) from inside the run.
  • Anything that depends on live settings stays "needs validation". I check those afterwards myself, read-only, through our own account APIs (section 7).

7. After the run

Fix loop

  • Every confirmed finding gets the smallest fix at the point where the decision is made, plus a regression test in test/security-*.test.js. The full suite (356 tests today) must pass before deploy.
  • A fresh agent checks each fix against the original proof test. A fix counts only when that proof now fails.
  • Critical and high get fixed and deployed first, medium in the same round, and low in one batch after that.
  • Where a fix changes something users see, it ships with my chosen default, and the summary says what changed.

Owner-side checks for "needs validation"

Read-only checks through our own API access:

  • The Cloudflare Worker and Pages settings (workers.dev off, routes, secrets present, API token scopes).
  • GitHub repo visibility.
  • The Google sign-in client's redirect list.
  • Dodo's webhook settings.
  • Instantly account limits.

What gets published

This site is public (noindex only), so the results page lists fixed findings and counts. Open findings stay in the local run folder until they're fixed.

9. What we're not building yet

Cloudflare's own advice for a small setup is to start with the skill and add harness stages only when their absence is what's slowing you down. So these wait:

  • A custom harness (database-backed stages, a separate dedup system). It waits until we audit more than 3 repos every month and comparing runs by hand gets slow. Then we build the minimal version Cloudflare describes: recon, hunt and validate in SQLite, with a validator that can't file its own findings.
  • Cross-repo tracing. Closefast's dependencies are external APIs, not our own repos, so there's nothing to trace yet.
  • Static analysis wiring (Semgrep). Cloudflare's hunters called it zero times in a month. They read and ran the code instead.
